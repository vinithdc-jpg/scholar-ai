# ScholarAI API Endpoints

This document describes the API routes currently present in the application.
Database-backed routes require PostgreSQL migrations to have been applied and
Firebase Admin credentials to be configured. Routes requiring unavailable
providers return an explicit `503 Service Unavailable` response.

## Base URL

Local development: `http://localhost:3000`

Production: use the deployed application URL.

## Authentication

The browser authenticates directly with Firebase Authentication. For protected
API requests, obtain a Firebase ID token with `user.getIdToken()` and send it
in the `Authorization` header:

```http
Authorization: Bearer <firebase_id_token>
```

Tokens are verified by Firebase Admin on the server. Missing or invalid tokens
are rejected. Firebase ID tokens expire; Firebase's client SDK refreshes them
when `getIdToken()` is called.

## Implemented endpoints

### Synchronize the signed-in user's profile

`POST /api/users/me`

Verifies the Firebase ID token and creates or updates the user's PostgreSQL
profile. The Firebase UID from the verified token is the profile identity;
email and display name are read from the verified token. Repeated requests
update the same profile rather than creating duplicate rows.

**Headers**

| Header | Required | Description |
| --- | --- | --- |
| `Authorization` | Yes | `Bearer <firebase_id_token>` |

**Request body**

No request body is required.

**Success — `200 OK`**

```json
{
  "user": {
    "id": 1,
    "firebase_uid": "verified-firebase-uid",
    "full_name": "Example Student",
    "email": "student@example.com",
    "role": "student",
    "created_at": "2026-01-01T00:00:00.000Z",
    "updated_at": "2026-01-01T00:00:00.000Z"
  }
}
```

The `id` and timestamp values are generated by PostgreSQL. The example values
are illustrative.

**Errors**

| Status | Example response | Meaning |
| --- | --- | --- |
| `400 Bad Request` | `{"error":"Your Firebase account must have an email address."}` | Verified Firebase account has no email. |
| `401 Unauthorized` | `{"error":"A Firebase sign-in token is required."}` | Missing Bearer token. |
| `401 Unauthorized` | `{"error":"Unable to verify your Firebase sign-in. Please sign in again."}` | Token is invalid or expired. |
| `500 Internal Server Error` | `{"error":"Firebase Admin authentication is not configured on the server."}` | Server-side Firebase Admin credentials are missing or invalid. |
| `500 Internal Server Error` | `{"error":"Unable to save your profile. Check the PostgreSQL connection and run npm run db:migrate."}` | Profile could not be persisted. |

## Endpoint behavior and requirements

### Authentication

`POST /api/auth/register` accepts `{ "email", "password", "name" }`, creates a
Firebase email/password user, saves the display name with Firebase Admin, and
synchronizes the PostgreSQL profile. It returns the user and refreshed Firebase
ID/refresh tokens so the token includes the saved display name. Configure valid
Firebase Admin credentials for registration.

`POST /api/auth/login` accepts `{ "email", "password" }` and an optional
`"superAdminOnly": true` flag for the dedicated super-admin page. The endpoint
verifies credentials with Firebase and, when requested, restricts sign-in to
the verified configured super-admin email. It returns a Firebase custom token
and synchronized user profile; the browser exchanges the token with Firebase
to establish its normal authenticated session. If configured,
`SUPERADMIN_PASSWORD` is checked server-side and is never included in the
client bundle.

`POST /api/auth/logout` requires a Bearer token and revokes Firebase refresh
tokens. The client calls this endpoint and then Firebase client `signOut()` to
clear its local auth state. Protected API routes check token revocation, so
previously issued tokens are rejected after logout. This adds a Firebase
revocation check to protected requests.

`GET /api/auth/me` requires a Bearer token and returns `{ "user": ... }`.

### Students

`GET /api/students/profile` returns the authenticated user's student profile or
`null`. `PUT` upserts it using the fields in the student profile schema in the
database migration. `GET /api/students/dashboard` returns saved-scholarship and
application counts plus upcoming verified scholarships.

### Scholarships

`GET /api/scholarships` and `/api/scholarships/search` accept `page`, `limit`,
`q`, `state`, `course`, `education_level`, and `scholarship_type` query
parameters. Results are published, verified scholarships only. `POST` creates
scholarships for content admins and super admins. `GET /[id]` reads a published
scholarship (or any scholarship for admins); `PATCH` updates it; `DELETE`
archives it. `GET /recommended` uses the signed-in student's profile to rank
current published scholarships.

`POST /api/eligibility/check` accepts `{ "scholarship_id": number, "profile"?: object }`.
If `profile` is omitted, the saved profile is used. It returns matched, failed,
and missing eligibility conditions and the official source URL.

### Saved scholarships and applications

`GET /api/saved-scholarships` and `GET /api/applications` accept `page` and
`limit`. Save a scholarship with `POST /api/saved-scholarships` and
`{ "scholarship_id": number }`; remove it with `DELETE /[id]`, where `id` is the
saved-record ID. Applications use `{ "scholarship_id": number, "student_notes"?: string }`
for creation. `PATCH /api/applications/[id]` updates status, notes, or
`applied_at`; `GET` also returns status history; `DELETE` removes the
application. Student ownership is enforced server-side.

### Documents

`POST /api/documents/upload` accepts multipart form data with a PDF `file`,
`title`, and `document_type`; optional fields are `scholarship_id`,
`academic_year`, and `source_url`. File size is limited to 10 MiB. Configure
Cloudinary to enable uploads and deletion. Students can access their own
documents; admins can access all documents.

### AI and admin

Chat session listing, retrieval, and deletion are implemented. `POST
/api/ai/chat` currently returns `503`: the grounded retrieval, embedding, and
citation pipeline is not yet implemented. Document ingestion likewise returns
`503` until its Redis/BullMQ worker is implemented.

Admin endpoints require a role stored in PostgreSQL (`content_admin` or
`super_admin`); audit logs are restricted to `super_admin`. Roles supplied by
the client are never trusted.

List endpoints accept `page` (default `1`) and `limit` (default `20`, maximum
`100`) unless otherwise specified. Protected endpoints require a valid Firebase
Bearer token.
